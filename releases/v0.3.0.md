# email 0.3.0

Attachments now work in the desktop app: add files to drafts, send them over SMTP,
include them when forwarding, and save received files through native Save as dialogs.

- Selected files are copied into redb in the same transaction as the updated draft.
  Drafts keep their attachments after restarting or moving/deleting the original files.
- Remove attachments individually. Files are reclaimed when no other draft or durable
  delivery entry references them. Delivery history still retains message content.
- Received attachments are cached with account, folder, UIDVALIDITY and UID isolation
  and can be saved offline after their first complete fetch. Older cached messages
  require an online fetch for their attachments.
- SMTP and Sent-copy retries preserve exactly the same MIME bytes, including attachments.
  A stale draft cannot overwrite or send an older revision after an attachment import.
- File names are normalised for local saving. Attachment files are never automatically
  opened, and the frontend has no arbitrary filesystem access.
- German and English labels, native file selection, progress states and window-close
  protection during file operations.

Limits: up to 50 attachments and 16 MiB total attachment data on outgoing messages;
25 MiB for the complete encoded message and for opening received messages. Complex
or deeply nested MIME is bounded. Servers can impose smaller message limits.

Validation includes binary/UTF-8/empty-file MIME round trips, atomic file import and
replacement, database reopen, shared attachment cleanup, UID isolation, forwarding,
picker cancellation, autosave, close protection and copy-only delivery retries.

This remains a technical preview. Safe HTML rendering, incremental synchronisation,
multiple active accounts and CalDAV synchronisation are still on the roadmap.
